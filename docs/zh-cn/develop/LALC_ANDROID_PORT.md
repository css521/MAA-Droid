# LALC Android 执行差异与回归

对照版本：LALC v5.0.0，提交 `431b432e22f0b0da08b95d7c478fa213be20b3e8`。
资源仍从 LALC 获取；下列差异由 Android 引擎适配，不修改安装目录中的上游 JSON。

再次对照的 AALC 提交：`4a32dc8e1c659b94eafabab3d76f65aec7efde05`。它仅提供 Android
实现参考，不参与资源安装、热更新或当前流水线执行。

| 场景 | LALC v5.0.0 | AALC 对应实现 | Android 适配 |
|---|---|---|---|
| 经验选关 | `task_action/luxcavation.py:exec_exp_select_stage`，关卡号 OCR 后按卡片坐标点击 | `tasks/daily/luxcavation.py:EXP_luxcavation`，入口模板按 x 从右往左尝试，最多点击三次并确认编队页；不识别数字 09 | 保留 LALC 编号选择、滑动与点击，只扩展完整 STAGE 标签的前导零识别 |
| 邮件 | `config/task/mail.json`，领取、等待、Esc 确认和退出 | `tasks/daily/get_prize.py:get_mail_prize`，点击领取确认与关闭模板 | 保留 LALC 节点和完成计数，以明确识别的邮箱状态和按钮适配手机输入 |
| 返回主页 | `workflow/task_execution.py:exec_back_to_init_page`，处理已知弹窗后默认 Esc | `tasks/base/back_init_menu.py:back_init_menu`，优先返回按钮、最后空白点击加 Esc | 确认采光选关页后立即走原 Esc；未知加载画面有界等待 |
| Android 按键 | 桌面键名 | `module/automation/input_handlers/simulator/simulator_control.py`，Esc=111，Enter=66 | 保持相同 Android 键码，不将 Esc 全局改为 Back=4 |

## 经验关卡 OCR

上游 `task_action/luxcavation.py` 在整帧掩码 `[250,180,1000,50]` 中查找配置的关卡号，
未命中时滑动重试，命中后使用该关卡横坐标加 10，点击 Enter（y=480）或 Skip Battle（y=515）。
Android 保留这些坐标、重试上限和用户配置中的前导零。

2026-09-10 的 751 日志已走到 `exp_select_stage`，最终报告找不到 09。
截图上 09 确实可见，模型装载和提权连接未报错，但日志没有当时 OCR 的原始帧或文本结果。
因此，截图回放不能证明手机失败时的确切输入。

直接归一后的截图能识别 09；对同一截图改变一像素裁剪边界和采样方式，可复现两处问题：

1. 低分噪声与正确的 07 合并后，整块的最低置信度使正确数字被过滤。
   上游 RapidOCR 3.8.4 会先按 `Global.text_score=0.5` 过滤单框，再交给
   `recognize/rapid_ocr.py` 合并。Android 已对齐此顺序。
2. 灰度增强在一个采样变体中把 09 识别成低分 9，保留原色则识别为 09。
   Android 对未命中的纯数字查询增加一次原色重试，使用同一帧和掩码、相同置信度。
   不放宽分数，不把 9 猜成 09，不允许 09 匹配到 109；名称查询保持上游包含语义。

`ExpStageNativeTest` 使用真实 det/rec 模型和仅包含关卡区域的截图夹具，
验证 07/08/09、同帧重试、目标数字边界、掩码、阈值以及两种按钮点击坐标。
夹具来源与转换步骤见 `engine/limbus/src/test/resources/ocr/README.md`。

754 的后续日志提供了直接证据：2026-09-10T04:53:40Z，frame3836 的增强和原色 OCR
均把 09 读为完整 `STAGE 9`（84% / 61%），旁边标题为 `Luxcavation #9`。纯字面查询
拒绝了这个结果，随后沿上游方向滑到低编号页。新增 `findExpStage` 只在原标题掩码里，
将完整 STAGE 标签按数值匹配，`STAGE 9` 可以匹配配置 09；单独的 `9`、标题 `#9`、
109 和 90 都不会误中 09。通用 `findText` 的数字边界和名称匹配不变。

对应低分辨率预览仅保留 542×305 像素，归一后模型只读出 08；该图作为不猜测关卡的
负例，不能用来声称 09 真机识别通过。真实日志候选有独立回归，高分辨率旧图仍用于
真实模型到点击坐标的正例回放。

## 保留页面重新执行

此前 Android 在没有 Drive 锚点的未知页面先等待三轮，这与上游普通页面立即 Esc
不同。采光选关页会折叠主页导航，因此会被错误提示“等待加载或登录”。现在用 LALC
的 `luxcavation` 标题确认选关页，必要时只在左侧标题区域以原阈值 0.85 多尺度匹配，
确认后立即执行上游 Esc。连接中提示优先于选关页；全部恢复仍受 20 次上限约束。

`RetainedPageNativeTest` 在最新截图中用原模板得到 0.86098，确认立即发送 Esc=111；
真实主页截图不会进入恢复，黑屏仍等待。没有提供发送 Esc 后的连续游戏帧，因此这项
验证证明页面识别与输入分支，尚不证明该手机上的返回转场成功。

## 领取邮件

上游 `config/task/main.json` 的 `task_center` 直接指向 `check_and_get_mails`，
依赖桌面坐标 `[1080,60,70,80]` 内的红色感叹号，而没有通过 `mail_entry`。
这使“已勾选邮件”不等于一定打开邮箱检查；同时 `check_mail` 关闭的是 `mail_entry`。
751 的两次失败运行都没有进入邮件节点，不能把任务队列中的 `mail` 当作已执行证据。

Android 在本次运行的流水线副本上使用已有的 `mail_entry` / `check_mail` 入口与完成计数，
先进入 Window、确认主页锚点，再打开手机邮箱；不再把通知红点缺失当作检查完成。
领取、等待连接和退出沿用上游 mail.json，空邮箱另有退出分支。
奖励确认会先识别空邮箱或奖励提示，再点击识别到的对应按钮；结果未确认时有界失败，
避免返回主页后仍按“邮箱非空”继续点击。仅这两张状态模板允许相同阈值的缩放匹配。
未勾选的邮件不会执行，完成后不会在同次运行重新进入。

资源安装在暂存目录中复用同一适配器检查邮件结构。即便上游默认关闭邮件，也按启用邮件
的副本验证后续可运行性；上游改变路由、识别方式或操作目标时，在资源激活前拒绝更新，
保留现有完整资源目录与版本。描述、时序、阈值、模板图片等兼容更新仍可安装。
验证与运行都只改内存副本，不把强制启用、Android 路由或标记写回上游 JSON。

`MailPipelineTest` 用实际 v5.0.0 JSON 和生产动作运行状态变化的模拟邮箱，覆盖
有邮件但无红点、空邮箱、未勾选、完成后转入经验任务、缺少主页锚点等场景。
这里验证的是流水线路由与输入序列；没有手机邮箱的连续实际画面，不能宣称真机领取已通过。

12:53 日志包中保留的 753 邮件运行和空邮箱截图进一步复现了问题：`no_mail_in_storage`
及奖励确认模板在该手机图上都未命中，连原有多尺度回退也无结果，因此一直停在确认节点。
邮箱适配增加独立 OCR 区域，在同一帧确认 Mailbox 标题、空邮箱文字和 Close 按钮；
按钮行单独重读，保持置信度 0.7，不猜测错拼按钮。只读到标题或空邮箱文字也表示邮箱
仍存在，但没有明确 Close 坐标时不会点击或当作已关闭。

空邮箱走已有 `exit_mailbox`；奖励确认和退出点击识别到的按钮。关闭后需再次确认邮箱
不再存在且 Window/Drive 主页锚点可见，才允许进入 `check_mail`。未转场会有界失败，
不重复领取、不提前报告完成。`MailboxNativeTest` 用用户的空邮箱图、真实模型及上游
JSON 复现“模板漏识别→OCR 识别→一次 Close 点击”，并证明保持原图时不会结算成功；
另测擦除 Close 的画面仍判断邮箱存在。它不证明手机接受点击后的实际状态变化。

## 任务结果

`LimbusTaskRun` 根据 `PipelineRunner` 的实际入口与检查计数报告任务事件。
进入任务入口才发出 `Started`；检查节点达到 `target_count` 并关闭对应 `disable_node`
时才发出 `Completed`。完成检查通过入口关联，不依赖检查节点固定名称。
从保留的镜牢结算页恢复可能直接进入 `mirror_check`，这同样是实际执行证据；
镜牢的完成语义沿用上游配置次数，不代表每次战斗均胜利。

邮件完成后若经验识别失败，邮件保持完成，经验报告失败，尚未进入的任务记为停止且注明
未开始。用户停止或协程取消不会改写已完成任务，取消仍向协程调用方传播。
仅到达 `end`、栈空或某个动作返回成功，不足以判定所选任务完成；缺少完成检查时整次运行
报告未完成。相同类型不能重复追加多个任务 ID，重复次数由任务配置指定。

`LimbusTaskRunTest` 与 `MailPipelineTest` 使用真实上游 JSON、生产检查动作和模拟游戏边界，
验证逐项结果、三次重复、自然结束但任务未完成、取消、重复任务拒绝和镜牢结算恢复。
资源更新测试则经过 `AtomicResourceInstaller`，核对拒绝更新后旧树的全部目录、文件与版本。

## 后续日志

新增 `diagnostics/events.log` 的 `limbus / ocr.find` 记录包含数字目标、帧序号、尺寸、
stride、掩码、候选文字及分数、原色重试结果和命中数。每次仅记录有限候选，不转储配置。
数字查找是选关动作的边界，不在持续截图循环中逐帧写盘。
经验专用查询使用 `ocr.exp_stage`；邮箱使用 `mail.ocr` 记录有限候选及 `mail.observe`
记录本帧状态和关闭坐标，便于区分具体适配结果。
仍可在应用快捷选项导出日志，无需 USB。
