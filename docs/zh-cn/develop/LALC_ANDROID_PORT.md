# LALC Android 执行差异与回归

对照版本：LALC v5.0.0，提交 `431b432e22f0b0da08b95d7c478fa213be20b3e8`。
资源仍从 LALC 获取；下列差异由 Android 引擎适配，不修改安装目录中的上游 JSON。

## 经验关卡 OCR

上游 `task_action/luxcavation.py` 在整帧掩码 `[250,180,1000,50]` 中查找配置的关卡号，
未命中时滑动重试，命中后使用该关卡横坐标加 10，点击 Enter（y=480）或 Skip Battle（y=515）。
Android 保留这些坐标、重试上限和前导零。

2026-09-10 的 751 日志已走到 `exp_select_stage`，最终报告找不到 09。
截图上 09 确实可见，模型装载和提权连接未报错，但日志没有当时 OCR 的原始帧或文本结果。
因此，截图回放不能证明手机失败时的确切输入。

直接归一后的截图能识别 09；对同一截图改变一像素裁剪边界和采样方式，可复现两处问题：

1. 低分噪声与正确的 07 合并后，整块的最低置信度使正确数字被过滤。
   上游 RapidOCR 3.8.4 会先按 `Global.text_score=0.5` 过滤单框，再交给
   `recognize/rapid_ocr.py` 合并。Android 已对齐此顺序。
2. 灰度增强在一个采样变体中把 09 识别成低分 9，保留原色则识别为 09。
   Android 对未命中的纯数字查询增加一次原色重试，使用同一帧和掩码、相同置信度。
   不放宽分数，不把 9 猜成 09，不允许 09 匹配到 109；名称查询保持上游包含语义。

`ExpStageNativeTest` 使用真实 det/rec 模型和仅包含关卡区域的截图夹具，
验证 07/08/09、同帧重试、目标数字边界、掩码、阈值以及两种按钮点击坐标。
夹具来源与转换步骤见 `engine/limbus/src/test/resources/ocr/README.md`。

## 领取邮件

上游 `config/task/main.json` 的 `task_center` 直接指向 `check_and_get_mails`，
依赖桌面坐标 `[1080,60,70,80]` 内的红色感叹号，而没有通过 `mail_entry`。
这使“已勾选邮件”不等于一定打开邮箱检查；同时 `check_mail` 关闭的是 `mail_entry`。
751 的两次失败运行都没有进入邮件节点，不能把任务队列中的 `mail` 当作已执行证据。

Android 在本次运行的流水线副本上使用已有的 `mail_entry` / `check_mail` 入口与完成计数，
先进入 Window、确认主页锚点，再打开手机邮箱；不再把通知红点缺失当作检查完成。
领取、等待连接和退出沿用上游 mail.json，空邮箱另有退出分支。
奖励确认会先识别奖励提示或空邮箱，再决定按返回键；结果未确认时有界失败，
避免返回主页后仍按“邮箱非空”继续点击。仅这两张状态模板允许相同阈值的缩放匹配。
未勾选的邮件不会执行，完成后不会在同次运行重新进入。

适配器在选中邮件的运行开始时核对依赖的节点结构；上游改变路由、识别方式或操作目标时
明确拒绝覆盖，不静默套用旧坐标。此检查目前是运行准备门槛，不是资源激活门槛。
邮件未勾选时不会因邮件结构变化阻止其他任务。

`MailPipelineTest` 用实际 v5.0.0 JSON 和生产动作运行状态变化的模拟邮箱，覆盖
有邮件但无红点、空邮箱、未勾选、完成后转入经验任务、缺少主页锚点等场景。
这里验证的是流水线路由与输入序列；没有手机邮箱的连续实际画面，不能宣称真机领取已通过。

## 后续日志

新增 `diagnostics/events.log` 的 `limbus / ocr.find` 记录包含数字目标、帧序号、尺寸、
stride、掩码、候选文字及分数、原色重试结果和命中数。每次仅记录有限候选，不转储配置。
数字查找是选关动作的边界，不在持续截图循环中逐帧写盘。
仍可在应用快捷选项导出日志，无需 USB。
